# 구독·결제 사건 상태기계 (설계 초안)

Refs #8.

- 상태: **초안(제안)**. 결제 공급자·가격·청구 주기·체험·환불 기준·유예 기간은 정하지 않습니다(이슈 제외 범위, #5 D-02). 실제 결제는 만들지 않습니다.
- 선행: 이슈 본문의 선행 #5(상품 계약 — `docs/design/product-tiers.md`)와 #7(권한 평가기, 미처리). 권한 평가기와 맞닿는 칸은 "#7 의존"으로 표시합니다.
- 코드 기준: main `fc3b16f`. 구독·entitlement 코드는 없습니다(2026-11-10 설계 감사, `subscription|entitlement` 검색에서 시장자료 경고 문구 외 0건).
- 작성: 2026-11-10 설계 감사.
- 보강: 2026-11-11 — #104 구현(PR #110) 리뷰에서 같은 주제의 지적이 반복되어 대사 규칙을 상세화(§5.1 정보 우선순위, §5.2 로컬 전용 필드 보존, §5.3 순번 없는 사건 경로, §5.4 새 구독 주기 정리).

## 1. 반영한 사용자 결정 (2026-11-10, #5 이슈 댓글)

| 결정 | 상태기계에 주는 영향 |
|---|---|
| 무료 = 로그인 필수 + R01·R07 | 구독이 없거나 끝나도 로그인 사용자는 무료 entitlement를 유지 |
| 유료 = 확장 기능 + 개인 계좌 분석 | 구독 상태가 `active`·`grace`(유예를 둔다면)일 때만 유료 entitlement |
| 수강생 = 수강 기간 동안 유료와 동일, **구독과 별도 권한** | 이 상태기계는 **구독만** 다룹니다. 수강생 권한은 별도 축(Learner grant)이고, entitlement = max(무료, 구독 유료, 수강 기간 중 유료) |

## 2. 원칙

1. **권한은 검증된 결제 사건으로만 오르내립니다.** 클라이언트 화면, 모델 입력, 결제 페이지 리다이렉트 결과 파라미터는 상태를 바꾸지 않습니다.
2. 사건은 서명 검증된 공급자 webhook 또는 공급자 API 조회 결과로만 받아들입니다(공급자는 결정 필요).
3. 상태 전이는 서버 한 곳(구독 저장소)에서만 씁니다 — 단일 writer.
4. entitlement는 상태에서 **계산**하고 따로 저장하지 않습니다(어긋남 방지). 캐시하면 사건 반영 즉시 무효화합니다.
5. 개인 금융정보(카드번호 등)는 저장하지 않습니다. 공급자 고객 ID·구독 ID만 저장합니다.

## 3. 상태

| 상태 | 유료 entitlement | 설명 |
|---|---|---|
| `none` | 아니오 | 구독 이력 없음 |
| `pending` | 아니오 | 결제 시작, 확정 사건 전 |
| `trialing` | 예(체험을 둔다면) | 체험 기간 — 체험 여부 **결정 필요** |
| `active` | 예 | 정상 |
| `past_due` | 결정 필요(유예) | 갱신 결제 실패, 재시도 중 |
| `canceled_pending_end` | 예(기간 끝까지) | 해지 예약, 현재 기간은 유지 |
| `expired` | 아니오 | 기간 종료 |
| `refunded` | 아니오 | 환불 완료 — 기간 남아도 즉시 종료(환불 규칙 **결정 필요**) |
| `disputed` | 결정 필요 | 지불 거절·분쟁 |

## 4. 사건과 전이

| 현재 | 사건(검증된 것만) | 다음 |
|---|---|---|
| `none`/`expired` | `checkout.completed` | `pending` |
| `pending` | `payment.succeeded` | `active` (체험이면 `trialing`) |
| `pending` | `payment.failed` / 시간 초과 | `none` |
| `trialing` | `trial.ended` + `payment.succeeded` | `active` |
| `trialing` | `trial.ended` + 결제 실패 | `past_due` 또는 `expired` (결정 필요) |
| `active` | `renewal.succeeded` | `active` (기간 연장) |
| `active` | `renewal.failed` | `past_due` |
| `past_due` | `payment.succeeded` 또는 `renewal.succeeded` (갱신 재시도 성공) | `active` (기간 연장) |
| `past_due` | 재시도 소진 / 유예 종료 | `expired` |
| `active`/`trialing` | `subscription.cancel_requested` | `canceled_pending_end` |
| `canceled_pending_end` | `subscription.resumed` | `active` |
| `canceled_pending_end` | 기간 종료 | `expired` |
| `active`/`canceled_pending_end`/`past_due` | `refund.succeeded` (전액) | `refunded` |
| `active` 등 | `dispute.opened` | `disputed` |
| `disputed` | `dispute.won` / `dispute.lost` | 이전 상태 / `refunded` |

사건 이름은 설명용이며 공급자 사건 이름에 맞춰 매핑합니다(공급자 결정 후). 표에 없는 (상태, 사건) 조합은 상태를 바꾸지 않고 기록한 뒤 공급자 API 조회로 현재 상태를 맞춥니다(§5 유실 대사와 같은 경로).

## 5. 멱등·순서 역전·중복·지연

| 문제 | 처리 |
|---|---|
| **중복 사건** | 공급자 사건 ID를 유일 키로 저장. 이미 처리한 ID는 200 응답만 하고 무시 |
| **순서 역전** | 사건마다 공급자 발생 시각과 구독 판본(공급자가 주는 순번이 있으면 그것)을 저장. 저장된 판본보다 오래된 사건은 상태를 되돌리지 않고 기록만 함. 순번이 없으면 사건을 받은 뒤 공급자 API로 현재 구독 상태를 조회해 그 값으로 맞춤 |
| **지연** | 기간 종료는 사건을 기다리지 않고 저장된 `current_period_end`로 계산. 만료 사건이 늦게 와도 그 사이 유료 entitlement는 이미 꺼져 있음 |
| **유실** | 주기적으로 공급자 API와 대사(주기 **결정 필요**). 차이가 나면 공급자 값 우선, 차이 기록 — 우선순위·보존 규칙의 상세는 §5.1–§5.4 |
| **서명 실패** | 거부(4xx), 상태 변화 0, 보안 기록 |
| **동시 처리** | 같은 구독의 사건은 구독 ID 단위로 직렬 처리 |

### 5.1 대사의 정보 우선순위 — 채택과 확인

대사는 서명 검증된 공급자 API 조회 결과(**공급자 뷰**)를 저장된 구독과 비교해 맞추는 절차입니다(§5 유실 행). 경로는 둘입니다.

| 경로 | 언제 | 저장 값에 하는 일 |
|---|---|---|
| **채택** (adopt) | 공급자 뷰가 저장 상태·기간과 다른 값을 줄 때 | 상태·기간을 공급자 값으로 바꾸고 차이를 기록. 기준점(`state_changed_at`) 초기화는 이때만 |
| **확인** (confirm) | 공급자 뷰가 저장 상태를 그대로 뒷받침할 때 | 상태·로컬 전용 필드(§5.2)·기준점을 그대로 두고, 공급자가 준 값(기간, 더 새로운 판본)만 갱신 |

값 사이의 우선순위 규칙:

| # | 충돌 | 규칙 | 근거 |
|---|---|---|---|
| P1 | 공급자 뷰 ↔ 저장 상태·기간 | 다르면 공급자 값 우선, 차이 기록(채택) | §5 유실 행 |
| P2 | 공급자 판본 ↔ 저장 판본 | 대사는 저장 판본을 앞당기기만 함 — 확인 경로에서도 더 새로운 판본을 보고하면 저장. 저장 판본보다 오래된 공급자 뷰는 채택하지 않고 기록 | §5 순서 역전 행: 판본은 되돌아가지 않음. 확인이 새 판본을 버리면 이후 오래된 사건이 수용됨 |
| P3 | 사건 판본 ↔ 저장 판본 | 사건 판본이 저장 판본 이하면 전이 없이 기록만 | §5 순서 역전 행 |
| P4 | 사건 판본이 저장 판본보다 새로울 때 | 전이표 조합이면 전이 적용, 표 밖 조합이면 기록 + 대사 필요(§5.3) | §4·§5 |
| P5 | 공급자 뷰 ↔ 로컬 전용 필드 | 공급자 뷰가 담지 않는 정보는 채택·확인 어느 경로에서도 덮어쓰지 않음 | §5.2 |
| P6 | 기준점 ↔ 대사 | 기준점 초기화는 상태가 실제로 바뀌는 채택에서만 | §5 지연 행 — 확인이 기준점을 덮어쓰면 유예·시간 초과가 결제 없이 재시작됨 |

공급자가 판본을 주지 않으면(B-01 확정 전의 가정) P2·P3 의 판본 비교는 성립하지 않고, 정합은 §5.3 의 대사 경로가 맡습니다.

예시 — 저장 `active`(판본 10)에 판본 5 의 `renewal.failed`가 늦게 도착 → P3 로 기록만. 이어 대사가 판본 12 의 `active` 뷰를 확인 → P2 로 저장 판본 12, 상태·기준점은 불변(확인).

### 5.2 대사가 덮어쓰지 않는 로컬 전용 필드

공급자 뷰가 말하는 것은 상태·기간·(주는 공급자만) 판본입니다. 아래 값은 저장소만 아는 정보라서 채택·확인 어느 경로에서도 지워지거나 재설정되지 않습니다.

| 필드 | 뜻 | 보존 이유 (지웠을 때 생기는 일) |
|---|---|---|
| `trial_ended` | 체험 정산 표지 — `trial.ended`를 받아 정산 결제(`payment.succeeded`)를 기다리는 중 | §4 체험 행은 이 표지가 있어야 `active` 로 전이. 확인 대사가 지우면 정산 결제가 표 밖 조합이 되어 `trialing`에 갇힘 |
| `state_changed_at` | 현재 상태가 시작된 시각 — 유예(B-04)·`pending` 시간 초과의 기준점 | now 로 재설정하면 만료된 유예·타임아웃이 결제 없이 대사마다 재시작(§5 지연) |
| `previous_state` | 분쟁 복구 상태 — `dispute.won`이 돌아갈 목표 | 없으면 분쟁 종결이 표 밖 조합이 되어 `disputed`에 갇힘(§4). 대사가 기간만 갱신할 때 보존, 대사가 놓친 분쟁 개시를 채택할 때 신규 포착 |
| `previous_state_changed_at` | 분쟁 복구 시 되돌릴 기준 시각 — `dispute.opened`가 `state_changed_at`을 따로 저장 | 분쟁 왕복(`past_due` → `disputed` → 복구)이 소진된 유예를 재시작하지 않게 함(`state_changed_at`과 같은 이유) |
| `replacement_checkout_pending` | 교체 checkout 대기 표지 — 판본 없는 `checkout.completed`가 표에 적용되지 못하고 뷰 대기 중(새 주기 후보) | 확인 대사가 지우면 정산까지 끝난 교체가 구기간에 갇혀 effective `expired`로 남음(§5.4 N1). 소비는 증거(판본 진전)가 있을 때만(N3) |

예시 — `trialing` + `trial_ended` 저장 중 대사가 공급자 뷰 `trialing`(기간 갱신)을 확인 → 표지 유지 → 이후 검증된 `payment.succeeded`가 `active` 로 정산.

이 표가 전부는 아닙니다. 공급자(B-01) 확정 뒤 공급자 뷰가 담지 않는 저장 필드가 더 생기면 이 표에 추가하며, 새 필드를 설계할 때 먼저 "공급자가 이 값을 말하는가"를 묻습니다.

### 5.3 순번 없는 사건의 처리 경로

| 규칙 | 내용 | 근거 |
|---|---|---|
| R1 | 순번 없는 사건은 도착 순서를 권위로 삼지 않음 — 전이를 적용하지 않고 기록 + 멱등 표시 + '대사 필요' 결과. 호출자가 공급자 뷰를 조회해 §5.1 대사로 맞춤 | §5 순서 역전 행("순번이 없으면 … 조회해 그 값으로 맞춤") |
| R2 | 순번 있는 사건도 (상태, 사건)이 표 밖 조합이면 상태 불변 + 기록 + '대사 필요' — 영구 unhandled 가 아님. 순서가 어긋나 도착한 사건(예: `checkout.completed`보다 먼저 온 `payment.succeeded`)이 갇히지 않게 함 | §4("표에 없는 조합은 … 조회로 맞춤") |
| R3 | '대사 필요'로 기록한 사건 ID 도 멱등 표시(재전달 무시) — 정합은 재전달 재적용이 아니라 대사가 맞춤 | §5 중복 사건 행 |
| R4 | 미주입 매개변수(B-03·B-04 계열)로 전이 대상을 정할 수 없는 사건은 unhandled 기록 유지 — 대사가 임의로 정하지 않음 | #104 완료 조건 3(결정 필요 값 고정 금지) |
| R5 | 대사 결과의 저장 반영도 같은 구독의 직렬 큐로 — 대사 전용 우회 경로를 만들지 않음 | §5 동시 처리 행, §2 원칙 3(단일 writer) |

예시 — 순번 없는 `renewal.failed`가 갱신 성공 뒤 늦게 도착 → R1(기록 + 대사 필요) → 공급자 뷰 `active` 확인 → 되돌림 없음. 순번 있는 `payment.succeeded`가 checkout 전에 도착 → R2(표 밖 → 대사 필요) → 이후 checkout·대사로 `active` 정합.

### 5.4 새 구독 주기 시작 시 이전 기간·기준점 정리

| 규칙 | 내용 | 근거 |
|---|---|---|
| N1 | `checkout.completed`는 새 구독 주기의 시작 — 이전 주기의 `current_period_end`를 물려받지 않음. 새 기간은 사건·대사 뷰가 줄 때만 설정하고, 주지 않으면 비어 시작. 정산이 이미 끝난 상태로 대사 뷰가 도달해도(중간 `pending` 미관찰) 같다 — 교체 증거(판본 진전 + §5.2 `replacement_checkout_pending`)가 있을 때만 이전 기간을 비움 | §5 지연 행: 만료된 기간을 물려받으면 새 `pending`이 즉시 `expired`로 계산되어 §4 전이가 무효화됨 |
| N2 | checkout 수용 판정은 저장 상태가 아니라 계산된(effective) 상태 기준 — 만료·시간 초과로 effective 가 `expired`/`none`이면 수용. 단 저장 상태가 `disputed`면 수용하지 않음 | §4 전이표(none/expired 기준)·§5 지연. `disputed` 제외는 복구 상태 소실 방지(§5.2) |
| N3 | 기준점 초기화는 새 주기가 실제로 시작될 때만(전이 적용 또는 대사 채택). 같은 상태를 확인하는 대사와 시간 경과만으로는 초기화하지 않음 — 버려진 checkout이 주기 대사마다 부활하는 것을 막음. '교체 checkout' 판정은 저장 값으로 구분되는 증거(판본 진전 등)일 때만 | §5 지연·§5.1 P6. 판정 세부 기준은 공급자 뷰 구성(B-01) 확정 뒤 다시 적음 |
| N4 | 분쟁 중 구독의 기간이 끝났을 때 공급자 뷰가 종결 상태(`expired` 등)를 확인하면 저장 상태를 그 값으로 맞춤 — 분쟁 관련 제한은 기간이 살아 있는 동안의 규칙 | §4("조회로 현재 상태를 맞춤")·§5 지연(effective 이미 만료). 채택하지 않으면 checkout·대사 어느 쪽으로도 회수 불가 |

예시 — 기간 만료 뒤 `checkout.completed`(기간 미포함) → N1 로 이전 기간 폐기, `pending` 시작 → `payment.succeeded` → `active`. 유예가 소진돼 effective `expired`인 `past_due`를 같은 공급자 뷰가 확인 → 기준점 보존으로 `expired` 유지(부활 없음).

## 6. entitlement 반영 (#7 의존)

- 상태가 바뀌면 그 사용자의 entitlement 캐시를 즉시 무효화하고, 다음 도구 호출에서 다시 계산합니다.
- 유료 → 무료로 내려가도 **사용자 PC의 계좌 자료는 지우지 않습니다**(#9 결정: 지울 때까지 보관). 유료 기능으로 다시 여는 것만 막습니다.
- 실행 중인 유료 작업은 `blocked`로 바꾸고 사용자에게 알립니다(`docs/design/durable-job-and-stock-link.md` §2.2).
- 수강 기간이 남아 있으면 구독이 끝나도 유료 entitlement가 유지됩니다(Learner grant 축).

## 7. 시험 설계

| # | 시험 | 기대 |
|---|---|---|
| S1 | 같은 `payment.succeeded`를 두 번 전달 | 상태 전이 1회 |
| S2 | `renewal.succeeded`가 `renewal.failed`보다 먼저 도착(발생은 반대) | 최종 `active`, 되돌림 없음 |
| S3 | 만료 사건 유실 | `current_period_end` 지나면 유료 entitlement 꺼짐 |
| S4 | 서명 불량 webhook | 거부, 상태 변화 0 |
| S5 | 결제 페이지 리다이렉트의 `success=true`만 있음 | 상태 변화 0 |
| S6 | 해지 예약 후 기간 중 | 유료 유지, 종료 시 무료 |
| S7 | 전액 환불 | 즉시 무료 |
| S8 | 구독 만료 + 수강 기간 중 | 유료 유지(Learner grant) |
| S9 | 구독 만료 + 수강 기간 종료 | 무료 |
| S10 | 유료 → 무료 전환 뒤 PC의 계좌 자료 | 그대로 있음, 유료 기능 호출은 `entitlement_required` |
| S11 | 같은 구독 사건 동시 2건 | 직렬 처리, 최종 상태 일관 |
| S12 | 대사에서 공급자와 다름 | 공급자 값으로 맞추고 기록 |
| S13 | 저장 데이터에 카드번호 등 결제 수단 원문 | 0건 |
| S14 | `renewal.failed` 뒤 갱신 재시도가 성공해 `renewal.succeeded` 도착 | `past_due` → `active`, 기간 연장, 전이표에 없는 (상태, 사건) 조합 0 |
